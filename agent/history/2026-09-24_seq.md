# 2026-09-24 — SEQ: the sequencer between MV and the robot link

Task: `agent/tasks/2026-09-24_mv-link-sequencer.md`. Closes the `[MISSING]` stage 6 that
`2026-09-16_firmware.md` listed first under Pending: *"Nothing sequences MV's primitives into F/T
lines. That is the missing piece between a plan and a moving robot."*

## Implemented
- **`project/src/SEQ`** — `seq::Sequencer`: a pure state machine
  (IDLE / WAIT_READY / SEND_LEG / WAIT_ACK / FINISHED / FAILED) that expands one MV primitive at a
  time into wire legs and sends exactly one, then waits for its `K`. No port, no clock, no heap.
  `tests/test_seq.cpp` — 15 groups, all passing on the PC.
- **`motivation/jetson/mission_runner.{h,cpp}`** — the platform half: the loop, the clock, the port,
  plus the plan-file reader. Nothing else.
- **`robot_link --run-plan FILE [--start-theta DEG] [--speed M_S] [--yaw-rate RAD_S]`**.
- `RobotState` gained `readies`; `constants.h` gained a `seq::cfg` block; CMake target `seq`;
  `tools/build_seq.sh`.

## Decisions (with the user)
- **A1 — `MOVE` is decomposed into `T` + `F`, not streamed as `M`.** Rejected: streaming `M`, which
  keeps the motion holonomic but leaves the leg with no acknowledgement, putting the robot back on
  the Jetson's timing — the exact thing option A was chosen to avoid on 2026-09-16. Also rejected:
  refusing `MOVE` outright, which would make MV's `holonomic=1` useless.
- **B — SEQ lives in `project/`, not `motivation/jetson/`.** The latter needs POSIX termios and does
  not build on Windows, so the state machine would have been untestable on this machine. Same
  reasoning that put LINK there.
- **C — `RobotState.readies`.** `ready` latches true on the first `READY` and so cannot tell a boot
  from a reboot mid-plan. A reboot zeroes the odometry, which voids the plan built on it.

## Four firmware facts that shaped the design
Read out of the code, not out of the docs. Each one would have produced a robot that hangs or
misbehaves if the sequencer had not been written around it.

1. **The `K` handshake is mandatory, not a courtesy.** `motion_task.cpp` pops a one-shot only while
   `!motion.busy()`, so legs sent back to back pile into an 8-deep FIFO and the ninth is dropped
   as `E 4`. One leg in flight, always.
2. **A leg the firmware refuses vanishes silently.** `applyOneShot` ignores the bool returned by
   `beginForward`/`beginTurn`. A leg under `mc::cfg::MIN_LEG_LENGTH_M` / `MIN_LEG_ANGLE_RAD`
   therefore produces no `K` and bumps no error counter — the sender would wait out the full ack
   timeout on every plan containing a rounding-sized leg. SEQ filters them with the same constants.
   This is the nastiest of the four and the one a future agent is most likely to reintroduce.
3. **Legs are timed, not pose-driven**, so a leg's duration is exactly computable: `rm::limitsFor`
   + `rm::TrapezoidalProfile`, the same call the firmware makes. The ack timeout is derived from it
   rather than guessed — the CLI's existing fixed 60 s would have been both too slow to notice a
   failure and, on a long plan, not obviously long enough.
4. **`READY` cannot be a gate.** The firmware may have booted long before the port was opened, in
   which case its `READY` is gone for good; waiting on it would deadlock. It is a grace period.

## The heading-bias problem, and why it is not obvious
`mv::toPrimitives` in its holonomic branch never advances the planned heading: every `MOVE` leaves
`theta` at `startTheta`, and the trailing `ROTATE` is `goalTheta - startTheta`. Decomposing a `MOVE`
turns the robot, so a naive decomposition makes that final `ROTATE` land in the wrong place.

SEQ therefore tracks two headings — `thetaPlan_` (what the plan assumes) and `thetaCmd_` (what has
actually been commanded) — and turns every `ROTATE(delta)` into the **absolute** heading
`thetaPlan_ + delta`, commanding `wrap(target - thetaCmd_)`. A non-holonomic plan has zero bias, so
it maps 1:1.

Checked end to end against the real planner: the same route planned with `holonomic 1` and
`holonomic 0` produces the **same six wire lines** (`T 64.926 / F 3.009 / T -36.098 / F 3.681 /
T 61.127 / S`) and the same final heading. That equality is the strongest evidence the bias
accounting is right, and it is worth re-running if anyone touches `toPrimitives`.

## Fail fast rather than wait out the timeout
`E 1`/`E 2` → FIRMWARE_REJECT, `E 4` → QUEUE_FULL, a new `READY` → REBOOTED, a dead port →
LINK_ERROR. Each emits `S`. Every counter is re-baselined at the moment the plan goes live, for two
reasons that are easy to miss: a boot zeroes the firmware's own tallies, and a fault raised before
the first leg went out cannot have been caused by us. `test_seq` covers both.

## Reviews
- `/code-standards-review`: 4 violations fixed. The interesting one: `FAULT_SLOTS` cannot live in
  `constants.h`, because it derives from `link::ErrCode` and `LINK/protocol.h` includes
  `constants.h`. It went into `SEQ/sequencer.h`, for the same reason `jetson::cfg::ERR_SLOTS` sits
  in its own module header.
- `/code-logic-review`: 1 mismatch fixed. `--speed` / `--yaw-rate` are user input and were not
  checked against the `link::cfg` accepted ranges, so `--speed 5` would have been rejected by the
  firmware as malformed on every leg — surfacing as a fault seconds into the run instead of as a
  refused `load()`.

## Pending
- Nothing below SEQ has run on hardware. `RobotLink` and the firmware are both still `[UNBUILT]`,
  so the chain is complete in code and unproven on a robot.
- **No frame reconciliation.** The firmware's odometry (`O`, zeroed at boot) and MV's room frame are
  unrelated, so `--start-theta` is supplied by hand and the pose printed during a run is the
  firmware's, not the room's. This blocks CM driving a plan end to end, and it blocks re-planning.
- Open loop by construction: SEQ trusts `K` and never compares `O` against where a leg should have
  ended. With no encoder there is nothing to compare against that would catch slip anyway.
- CM still cannot start a run (`/api/run` over `/api/plan` output), and the ZMQ bridge on 5555/5556
  remains the one documented interface with no implementation. That is the last break in the chain.
