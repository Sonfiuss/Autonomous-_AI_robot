# 2026-09-13 — MC module (motion executor: MV primitives -> per-wheel speeds)

## Implemented
- New C++ module `project/src/MC` + `include/MC` (roadmap L5). Takes the primitive list MV produced
  plus a commanded speed, returns one row per control tick: achieved body velocity, the three wheel
  speeds (rad/s) and the pulse rate + direction per wheel.
  - `speed_limit`: feasible chassis speed and ramp for a direction of travel.
  - `executor`: trapezoid per leg, mid-tick sampling, world-to-body rotation for MOVE legs, slew guard,
    step/dir conversion. STOP holds until the wheels are genuinely at rest.
  - `mc_api`: C API `mc_run`, `mc_max_speed`, `mc_status_text`, `mc_version`; not re-entrant, like MV.
  - `tools/mc_cli.cpp` (text driver, prints the trajectory table), `tools/build_mc.sh`.
  - `tests/test_mc.cpp`: 8 cases, including a real MV plan executed end to end and integrated back to
    a pose. All pass. MV and RM suites re-checked because `config/constants.h` is shared.

## Decisions (with user)
- MC is its own module, not a class inside RM and not Python (user chose, 2026-09-13). RM stays pure
  stateless maths; MC owns the cross-tick state. MC depends on RM only; MV is linked by the test alone.
- Output is a per-tick trajectory rather than per-primitive constants or ESP32 serial commands
  (user chose). Per-primitive rows cannot drive steppers, since the ramps are missing.
- MC contains no maths of its own. Every value comes from an RM call: `TrapezoidalProfile`,
  `OmniKinematics`, `VelocityProfile`, `DriverStepDir`, `Odometry`.
- Speed is scaled as a whole vector, never clipped per wheel: clipping one wheel bends the robot off
  the planned line. Consequence: the chassis is not equally fast in every direction.
  Measured at the current constants: 0.62 m/s forward, 0.54 m/s sideways, 2.57 rad/s spinning.
- Defaults 0.15 m/s, 0.8 rad/s, 50 Hz tick. The tick is 50 Hz while `interfaces.md` records 20 Hz for
  the older PoseController; not reconciled, MC takes dt per call.
- Velocity is sampled at the middle of each tick, matching the mid-point integration `rm::Odometry`
  already uses, which keeps the travelled distance accurate at 50 Hz.

## UI (step 10, added the same day on request)
- `McStep` gained `x, y, theta`, the pose after each tick, so callers can draw the motion without
  integrating anything. That bumped `mc_version` to 2. The executor already ran an `rm::Odometry`
  per tick, so this exposes work it was doing anyway.
- `project/src/CM/mc_client.py` (ctypes, mirrors mv_client) and `POST /api/trajectory`, which runs MV
  then MC and returns the plan, the per-tick rows and the `origin` those rows are relative to.
- CM page: a trajectory player under the map. Play or scrub moves an orange robot along the path while
  a canvas chart draws the three wheel speeds with a marker at the current tick, and a readout prints
  wheel rad/s, pulse Hz, body velocity and pose.
- Long routes are thinned to `MC_UI_MAX_ROWS` (600) by an integer stride so the JSON stays small; the
  full trajectory is always executed and playback multiplies `tick_s` by the stride to stay real time.
- Poses in the reply are displacements from the trajectory start, not world coordinates. The page adds
  `origin`. This is documented in `interfaces.md` because it is easy to get wrong.

## Interface changes
- New MC C API documented in `agent/description/interfaces.md`: `mc_run(McRequest, McResult)` and
  `mc_max_speed`. `McPrimitive.type` reuses MV's codes (0 ROTATE, 1 FORWARD, 2 MOVE, 3 STOP), now
  pinned by static asserts in `include/MC/types.h`.
- `McResult` reports the pose reached (`end_x`, `end_y`, `end_theta`) integrated through `rm::Odometry`,
  so a caller can check where a trajectory lands without replaying it.
- `config/constants.h` gained a `namespace mc` block; the RM and MV blocks are unchanged.
