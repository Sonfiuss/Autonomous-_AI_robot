# 2026-09-16 — ESP32 firmware, Jetson link, shared protocol, and MC's demotion

## Implemented
- **`project/LINK`** — the Jetson↔ESP32 wire protocol in ONE implementation, compiled into both
  sides. `LineAssembler`, `parseCommand`/`parseTelemetry`, formatters, `ErrorCounters`.
  `tests/test_link.cpp` passes on the PC.
- **`motivation/esp32_unified_controller/`** — ESP-IDF firmware: four FreeRTOS tasks
  (Comm / Motion / Peripheral / Status), three drivers (uart_link, step_dir_driver, servo_driver),
  `MotionState` (IDLE / RUNNING_LEG / ESTOP), `rt_port` (Mailbox / Queue / Flag / Snapshot with a
  host shim), `RobotContext`. `tests/test_motion.cpp` passes on the PC.
- **`motivation/jetson/`** — `SerialPort` (termios), `RobotLink` (commands, telemetry, keep-alive),
  a CLI (`--monitor`, `--vel`, `--forward`, `--turn`, `--stop`, `--reset`, `--servo`).
- **`agent/description/system_architecture.md`** — the pipeline as it actually is, per-stage I/O,
  plus an artifact page with the same diagram.
- **`speed_limit` moved MC → RM** (task `2026-09-16_speed-limit-to-rm.md`).

## Decisions (with the user)
- **Option A**: the ESP32 owns the kinematics. The Jetson sends intent (`M`/`F`/`T`), never per-wheel
  speeds. Option B (a `W w1 w2 w3` line with the Jetson doing the maths) was rejected: it leaves the
  robot driving blind whenever the link stalls.
- Consequence, and the thing that confused us for several exchanges: **MC is no longer on the live
  path.** It is a preview and feasibility tool. Documented as such now, in four places.
- **Option B for MC itself** (2026-09-16): keep MC, demote it in the docs, and move `speed_limit` to
  RM. Deleting MC was considered and rejected — it would cost `/api/trajectory`, the wheel-speed
  chart the user asked for on 2026-09-13, and `test_mc`'s end-to-end odometry replay. Merging MC's
  `Executor` with the firmware's `MotionState` was also considered: correct in principle, but a
  refactor of working tested code, and the two genuinely differ (batch walk vs. reactive tick).
- `M` is **body frame**. `interfaces.md` was silent and `2026-09-07_rm.md` had it open.
- Framework **ESP-IDF**, tick **50 Hz**, pin map **placeholders**.
- New wire line `E <code> <count>` for error counters. CRC and sequence numbers deliberately
  deferred: either changes all eleven lines and both sides at once.

## Two safety properties the tests forced out
- **The e-stop latches.** The first version left ESTOP as soon as the wheels stopped, so a streamed
  `M` that was still arriving restarted the robot immediately after a stop. `test_motion` caught it.
  Only `clearStop()` or a new explicit move releases it now.
- **A stale velocity is zero.** An `M` older than `MOTION_CMD_TIMEOUT_MS` (200 ms) counts as zero, so
  pulling the cable stops the robot and a finished `F` leg cannot resume a long-dead command. The
  three timeout constants live in `link::cfg` because they bind both sides.

## Pending
- Nothing sequences MV's primitives into `F`/`T` lines. That is the missing piece between a plan and
  a moving robot; the CLI is currently the only way to send one.
- No frame reconciliation between the ESP32's odometry (`O`, reset at boot) and MV's room frame.
- Real pin map; `MAX_PULSE_HZ` still a 20 kHz guess; direction signs unverified on hardware.
- Neither the firmware nor the Jetson app has ever been built for its real target on this PC. What is
  verified: `test_link`, `test_motion`, plus a full syntax check against hand-written ESP-IDF/POSIX
  stubs (scratchpad only, nothing added to the repo).
- `/code-standards-review` and `/code-logic-review` have not been run on any of this yet.

## Interface changes
- `interfaces.md`: `E <code> <count>` + its code table, the body-frame decision, the shared LINK
  implementation, and the streaming-watchdog section.
- `config/constants.h` gained a `link::cfg` block (framing, accepted ranges, the three watchdog
  constants) and `rm::cfg::MIN_WHEEL_COEFF`; `mc::cfg` lost the latter.
- `rm::limitsFor` / `rm::peakWheelOmega` / `rm::AxisLimits` are new RM API; `MC/speed_limit.h` is gone.

## Found, not caused by this work
`tests/test_rm.cpp` "accumulator carries fraction" fails when built `-O2` with MinGW's default x87
maths, and passes without `-O2` or with `-mfpmath=sse`. `StepAccumulator` sums `150 Hz × 0.01 s` and
x87's 80-bit intermediates move where the truncation lands. The ESP32's FPU carries no excess
precision so it behaves like the SSE case, but this accumulator feeds odometry. Worth its own task.
