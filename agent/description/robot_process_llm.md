# Roadmap: Natural-Language-Commanded Robot (LLM → Motion)

> Version 0.1 — 2026-09-09
> Scope: Phase 1 — the robot receives a natural-language command over serial, understands its spatial context, asks for clarification when the command is ambiguous, and drives to the target location.

---

## 1. Goals and Design Principles

### 1.1 Phase 1 Goal

The user types a command over serial (or a default command is used), e.g. *"Move next to the red table"*. The system:

1. Interprets the command in the current spatial context (which objects exist, where they are, which sides are free).
2. Asks follow-up questions when information is missing (which side? which table?).
3. Computes the goal pose and a sequence of simple motion primitives.
4. Converts that sequence into pulses for the motor drivers and executes it.
5. Reports the outcome (arrived / obstacle encountered).

### 1.2 Non-Negotiable Principles

| Principle | Rationale |
|---|---|
| **The LLM handles language and symbols only — never geometry.** It reads a scene-graph JSON and returns a *semantic goal* (`go to the right side of table_1`), never distances or turn angles. | LLMs are poor at arithmetic, non-reproducible, and slow (hundreds of ms to seconds). |
| **Everything involving coordinates, distances, and pulses is deterministic code.** | Testable, debuggable, real-time capable. |
| **Every LLM output passes through a code validator** before reaching lower layers. | A hallucination must never become physical motion. |
| **Pulses are generated on an MCU with hardware timers, never on the machine running the LLM.** | Linux cannot guarantee even timing. |
| **Inter-layer protocols are frozen from day one.** The fake MCU and the real MCU speak the same serial protocol. | Swapping simulation for hardware is a serial-port change. |
| **Build bottom-up, test each layer in isolation.** | When the robot drives wrong, you immediately know whether geometry or the LLM is at fault. |

## 2. Overall Architecture — 6 Layers

```
 [Serial / default command]
          │  text
          ▼
 ┌─────────────────────────────┐      ┌──────────────────────────────┐
 │ L2. Grounding & Dialog (LLM)│◄─────│ L1. Perception & World Model │
 │  text + scene graph → JSON  │      │  camera/lidar → scene graph  │
 └─────────────┬───────────────┘      └──────────────────────────────┘
               │ {goal | ask | primitive}
               ▼ (code validator)
 ┌─────────────────────────────┐
 │ L3. Goal Resolver (geometry)│  (target_id, relation) → goal pose (x, y, θ) in world frame
 └─────────────┬───────────────┘
               ▼
 ┌─────────────────────────────┐
 │ L4. Path Planner            │  current pose → goal pose → [ROTATE, FORWARD, ROTATE]
 └─────────────┬───────────────┘
               ▼
 ┌─────────────────────────────┐
 │ L5. Frame & Kinematics      │  world → body frame → wheel velocities; odometry back up
 └─────────────┬───────────────┘
               ▼ serial: M,N_L,N_R,f*CS
 ┌─────────────────────────────┐
 │ L6. Pulse Generation (MCU)  │  trapezoidal profile → step/dir → driver → motor
 └─────────────────────────────┘
               ▲ DONE / STOP,OBS (feedback up to L5, L2)
```

### 2.1 Layer Descriptions

#### L1 — Perception & World Model
- **Job:** turn sensor data into a scene-graph JSON.
- **Components:** RGB-D camera (RealSense D435 / OAK-D) + open-vocabulary detector (YOLO-World or Grounding DINO) → 2D pose (x, y, yaw) + dimensions per object; occupancy grid from lidar (RPLidar A1) or depth.
- **Derived fields:** `free_sides` — place the robot footprint on each of the object's 4 sides and check the grid; `near` — nearest landmark so the LLM has vocabulary for disambiguation questions.
- **Phase 1:** replaced by a hand-written scene graph / one generated by the 2D simulator. The real camera comes last.

#### L2 — Grounding & Dialog (LLM)
- **Input:** command + scene graph + conversation history.
- **Output:** JSON conforming to a fixed schema (structured output / tool-use), one of three types: `goal`, `ask`, `primitive`.
- **Decision logic (in the prompt, re-checked in code):**
  - Reference matches > 1 object → `ask` (use `near` to disambiguate).
  - No `relation` given and the object has multiple `free_sides` → `ask`, listing the free sides.
  - Exactly one free side → choose it and announce it.
  - Command is already a direct motion ("forward 1 m", "turn left 90°") → `primitive`, skip L3–L4.
- **Code validator after the LLM:** `target_id` exists in the scene graph; `relation` ∈ `free_sides`; primitive values within safety limits. Otherwise reject and re-ask.
- **Model:** start with a cloud API (Claude / GPT) with tool-use; once stable, move to a local model on Jetson (Qwen2.5 3B–7B, Llama 3.2 3B).

#### L3 — Goal Resolver (pure geometry)
- `(target_id, relation, clearance)` → goal pose in the world frame.
- For an object with center `(xₜ, yₜ)`, heading `ψ`, half-width `w/2`:
  ```
  offset_body = [0, -(w/2 + clearance)]     # "right" side, in the object's frame
  goal_xy     = [xₜ, yₜ] + R(ψ) · offset_body
  goal_theta  = ψ + π/2                     # face the object
  ```
  The four sides differ only in `offset_body`.
- Post-check: goal cell is free on the grid and the robot footprint fits.

#### L4 — Path Planner → motion-primitive sequence
- **Frozen primitive set:** `ROTATE(θ_rad)`, `FORWARD(d_m)`, `ARC(r_m, θ_rad)`, `STOP`.
- **Stage 1:** turn–go–turn: rotate toward the goal (`atan2`), drive straight (`hypot`), rotate to `goal_theta`.
- **Stage 2:** A* on the occupancy grid → compress the path into straight segments + turns → same primitive set.

#### L5 — Frame Transform & Kinematics
- **World → body:** `goal_body = R(−θ_robot) · (goal_world − p_robot)`.
- **Localization:** wheel-encoder odometry + IMU (EKF / complementary filter for yaw). Later: SLAM (slam_toolbox / ROS 2).
- **Differential-drive kinematics** (wheel separation `L`):
  ```
  v_L = v − ω·L/2,   v_R = v + ω·L/2
  ROTATE:  v = 0  →  v_L = −v_R
  FORWARD: ω = 0  →  v_L =  v_R
  ```
- If mecanum 4-wheel: adds `v_y`, a 4×3 matrix, and lateral motion → changes L4 as well. **Lock the mechanical configuration early.**

#### L6 — Pulse Generation (MCU)
- MCU: ESP32 / STM32 / Arduino + TMC2209 / A4988 drivers (steppers) or H-bridge + encoders (DC).
- Conversions:
  ```
  f_pulse [Hz]         = v_wheel / (2π·r) · steps_per_rev · microstep
  N_pulse (FORWARD d)  = d / (2π·r) · steps_per_rev · microstep
  ```
- Trapezoidal profile (accelerate – cruise – decelerate) — FastAccelStepper / AccelStepper.
- With DC motors: velocity PID loop → PWM; encoders feed odometry to L5.
- Safety sensors (ultrasonic / bumper) trip on the MCU, without waiting for upper layers.

## 3. Inter-Layer Interfaces (frozen at Milestone 0)

### 3.1 Scene graph (L1 → L2, L3)
```json
{
  "robot": {"x": 0.0, "y": 0.0, "theta": 0.0, "frame": "world"},
  "objects": [
    {"id": "table_1", "class": "table", "color": "red",
     "x": 2.1, "y": 0.4, "yaw": 0.0, "w": 1.2, "l": 0.8,
     "free_sides": ["right", "front"], "near": ["door"]},
    {"id": "table_2", "class": "table", "color": "red",
     "x": 4.0, "y": -1.5, "yaw": 1.57, "w": 1.2, "l": 0.8,
     "free_sides": ["left"], "near": ["window"]}
  ]
}
```

### 3.2 LLM output (L2 → validator → L3/L4)
```json
{"type": "goal",      "target_id": "table_1", "relation": "right", "clearance_m": 0.3}
{"type": "ask",       "question": "There are two red tables: the one near the door or the one near the window?", "candidates": ["table_1", "table_2"]}
{"type": "primitive", "cmd": "forward", "value": 1.0}
```

### 3.3 Motion primitives (L4 → L5)
```
ROTATE  <theta_rad>
FORWARD <d_m>
ARC     <r_m> <theta_rad>
STOP
```

### 3.4 Serial protocol Pi ↔ MCU (L5 ↔ L6)
```
Pi → MCU:   M,<N_L>,<N_R>,<f_max>*<checksum>\n      e.g.  M,1600,-1600,800*7A
MCU → Pi:   DONE,<N_L_actual>,<N_R_actual>\n
            STOP,OBS\n
            ERR,<code>\n
```
Checksum: XOR of all bytes before `*`, printed as 2 hex chars. Per-command timeout: `N/f` + 50% margin.

## 4. Simulation Strategy — 3 Levels

| Level | What it is | Tests layers | Tooling | When |
|---|---|---|---|---|
| **S1** | Hand-written scene-graph JSON, no simulation | L2 (LLM, dialog, validator) | JSON files + script calling the LLM | Week 1 |
| **S2** | Virtual 2D map: occupancy grid + object list + kinematic robot + **fake MCU on the same serial protocol** + viewer | L3, L4, L5, and the end-to-end pipeline | Python + numpy + pygame/matplotlib (or web canvas + WebSocket) | Core of Phase 1 |
| **S3** | Physics simulation (Gazebo / Webots / Isaac Sim) | L1 with rendered images, dynamics | ROS 2 | Not needed in Phase 1 |

### 4.1 Components of S2
- **Occupancy grid:** e.g. 10 m × 10 m at 5 cm resolution → 200 × 200 cells; walls and objects rasterized onto it.
- **Object list:** pose + dimensions → scene graph generated automatically; `free_sides` computed from the grid.
- **Virtual robot:** differential-drive integrator every `dt`:
  `x += v·cosθ·dt; y += v·sinθ·dt; θ += ω·dt` (+ small Gaussian noise to mimic wheel slip).
- **Fake MCU:** accepts the exact `M,N_L,N_R,f` frame, converts pulses back to distance, moves the virtual robot, returns `DONE`. Footprint collision check → returns `STOP,OBS`.
- **Viewer:** grid, colored objects with id labels, robot with heading arrow, goal pose computed by L3, path trace.

### 4.2 Regression scenario suite (one JSON file per scenario)
Contents: map + robot pose + command + expected dialog turns + expected goal pose (± tolerance).

Minimum set:
1. One red table, one free side → no question, drive straight there.
2. One red table, several free sides → ask "which side", receive answer, drive.
3. Two red tables → ask "which table" (using landmarks), then ask/not ask about the side.
4. Direct command "forward 1 m" → `primitive`, skip L3–L4.
5. Non-existent reference ("the blue table") → `ask`/reject, no motion.
6. Obstacle on the straight-line path → `STOP,OBS`, reported to the user.
7. LLM returns malformed JSON / `relation` not in `free_sides` → validator blocks it.

## 5. Milestone Roadmap

Order: **bottom-up**, each milestone with measurable acceptance criteria. Time estimates assume one person part-time; adjust to reality.

### M0 — Lock decisions & interfaces (≈ 1 week)
**Tasks**
- Lock the drive configuration: 2-wheel differential vs. 4-wheel mecanum; stepper vs. DC + encoder; MCU (ESP32 / STM32 / Arduino); LLM host (Pi 5 / Jetson / laptop initially).
- Lock the LLM: cloud API first, local later.
- Freeze the 4 interfaces in Section 3 into `interfaces.md` + JSON schemas.
- Measure and record mechanical constants: `r_wheel`, `L`, `steps_per_rev`, `microstep`, robot footprint.

**Acceptance:** interface doc committed; mechanical constants in `config.yaml`.

### M1 — Layer L6: MCU generates correct pulses (≈ 1–2 weeks)
**Tasks**
- Firmware receives `M,N_L,N_R,f`, verifies checksum, runs trapezoidal profile, returns `DONE`.
- Safety interrupt from ultrasonic/bumper → `STOP,OBS`.
- Python script to send commands by hand over serial.

**Acceptance:** `FORWARD 1.0 m` measured with a tape within 2%; `ROTATE 360°` within 5°; 10 repetitions consistent; triggering the contact sensor mid-run stops the robot in < 100 ms.

### M2 — Layer L5: Kinematics + odometry (≈ 1–2 weeks)
**Tasks**
- `kinematics.py`: primitive → `(N_L, N_R, f)`; odometry from `DONE` feedback (and encoder/IMU if available).
- World ↔ body frame transforms.
- Unit tests for both conversion directions.

**Acceptance:** the sequence `FORWARD 1.0 → ROTATE 90° → FORWARD 1.0 → ROTATE 90°` × 2 (a square) returns to the start within 10 cm on the real robot; odometry estimate matches the true position within that tolerance.

### M3 — S2 simulator + fake MCU (≈ 1–2 weeks, can run in parallel with M1–M2)
**Tasks**
- Build the grid, object list, virtual robot, fake MCU, viewer.
- Generate the scene graph from the object list; compute `free_sides`.
- Regression scenario suite as JSON + automated runner.

**Acceptance:** the same L5 code runs against both the fake MCU and the real MCU by changing only the serial-port parameter; all 7 scenarios in Section 4.2 run (without the LLM — hand-written `goal` commands).

### M4 — Layers L3 + L4: Goal resolver & turn-go-turn (≈ 1 week)
**Tasks**
- `goal_resolver.py`: 4 sides + clearance + grid check.
- `planner.py`: turn-go-turn; hook reserved for A*.
- Test in the simulator with hand-written `goal` commands.

**Acceptance:** in simulation, for every (object, free side) pair in the scenario suite, the robot reaches the goal pose within 5 cm and 5°; the goal pose never lands in an occupied cell.

### M5 — Layer L2: LLM grounding & dialog on a fake scene graph (≈ 2 weeks)
**Tasks**
- System prompt + tool schema for the 3 output types.
- Code validator.
- Multi-turn dialog loop over serial (or terminal) with short-term memory.
- Measure latency and accuracy on the S1 scenario suite.

**Acceptance:** ≥ 95% of scenarios return the correct type and `target_id`; 100% of schema-violating outputs blocked by the validator; zero cases of motion when the reference does not exist.

### M6 — End-to-end integration in simulation (≈ 1 week)
**Tasks**
- Wire L2 → validator → L3 → L4 → L5 → fake MCU.
- `DONE` / `STOP,OBS` feedback flows back to L2 to inform the user.
- Run the full scenario suite automatically, with the LLM in the loop.

**Acceptance:** demo "Move next to the red table" → asks which side → answer → asks which table (if two) → virtual robot arrives at the correct spot, repeatably.

### M7 — Real robot with a fake scene graph (≈ 1 week)
**Tasks**
- Swap fake MCU → real MCU; lay out the real room to match the virtual map (measure table positions by hand, enter them in the object list).
- Verify final pose with a tape measure.

**Acceptance:** the M6 scenario on the real robot with goal error < 15 cm (odometry drift accepted).

### M8 — Layer L1: Real perception (≈ 2–3 weeks)
**Tasks**
- RGB-D camera + YOLO-World / Grounding DINO → object pose + dimensions.
- Lidar/depth → occupancy grid; compute `free_sides`, `near` automatically.
- Replace the fake scene graph with the real one; L2–L6 unchanged.

**Acceptance:** auto-generated scene graph matches hand measurements within 10 cm; the M7 scenario runs without manually entering table positions.

### Post–Phase 1 (backlog)
- A* / DWA replacing turn-go-turn; SLAM replacing pure odometry.
- Local LLM on Jetson.
- Mecanum drive / manipulator arm if applicable.
- S3 simulation (Gazebo) when perception needs large-scale testing.

## 7. Risks and Mitigations

| Risk | Symptom | Mitigation |
|---|---|---|
| LLM invents distances/angles | Output contains numbers when none were requested | `goal` schema has no numeric fields; validator rejects. |
| Accumulated odometry drift | Error grows with the number of primitives | Cap primitives per command; add IMU; SLAM in a later phase. |
| Stepper missed steps | `FORWARD 1 m` falls short | Lower acceleration in the trapezoidal profile; check driver current. |
| LLM latency slows the dialog | > 3 s per turn | Trim the scene graph (send only relevant objects); cache; smaller model. |
| Wrong color/class detection | Scene graph doesn't match reality | Keep the fake scene graph as a baseline for comparison; confidence thresholds. |
| Serial protocol drops bytes | Repeated checksum failures | Bounded retries; MCU never executes a corrupt frame. |
